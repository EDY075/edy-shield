# ADR-003: UI Estática v1 (HTML) + Streamlit opcional v2

- **Status:** Aceito
- **Data:** 2026-08-01
- **Decisores:** jr (Tech Lead), ORION (UI/UX Designer), ATLAS (Arquiteto)
- **Referenciado em:** `ARCHITECTURE.md` §2, §3, §6

## Contexto

O EDY Shield é uma plataforma defensiva: os usuários precisam de uma interface para usar os módulos (Hash Checker, Log Analyzer, etc.) não apenas CLI.

Três opções foram consideradas:
- **HTML estático** (index.html + CSS + JS puro, no server.py)
- **Streamlit** (App UI rica com dashboards interativos)
- **FastAPI** (Backend REST + front-end separado)

Cada opção tem trade-offs.

## Decisão

A interface gráfica segue um roadmap em duas fases:

- **v1 (0.1.0 — v1.1):** Interface HTML estática com servidor HTTP stdlib (`ThreadingHTTPServer`). Sem frameworks, sem dependências externas de UI. A interface não contém lógica de negócio — apenas chama `/api/scan` etc.
- **v2+ (2.0+):** Dashboards interativos em **Streamlit** — quando houver múltiplos módulos e visualizações de cibersegurança.

Motivos:
- Sustentável (coincional) na v1, mantendo zero deps (ADR-001)
- Streamlit seria adicionado apenas como dependência opcional em v2+
- Transição suave: a API REST (`server.py`) já está pronta, Streamlit consumiria os mesmos endpoints

## Consequências

### Positivas
- ✅ Zero deps na UI (v1) — conforme philosophy do projeto
- ✅ UX boa o suficiente para uso em desenvolvimento e demonstração
- ✅ Arquitetura de plugins completamente separada da UI

### Negativas
- ⚠️ Sem framework: precisamos gerenciar rotas manualmente (server.py))
- ⚠️ Falta de autocomplete/testes de UI interativos na v1
- ⚠️ Para evoluir para Streamlit: instalação adicional, mas a lógica é intermédia (PluginManager separado)

## Pendências
- v2.0: implementar dashboard Streamlit se múltiplos módulos exigirem visualização dimensional
- Opcional: modo `--ui streamlit` ou `--ui html` como argumento CLI
