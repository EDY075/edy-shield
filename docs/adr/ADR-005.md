# ADR-005: Erros de domínio customizados — hierarquia única

- **Status:** Aceito
- **Data:** 2026-08-01
- **Decisores:** jr (Tech Lead)
- **Referenciado em:** `app/core/exceptions/domain.py`, `plugins/plugin_errors.py`, `ARCHITECTURE.md` §8

## Contexto

Com a evolução da plataforma com múltiplos módulos (Hash, Log, Reports), exceções Python stdlib como `ValueError`, `TypeError` e `OSError` tornaram-se ambíguas. Um `TypeError` pode ser de algoritmo inválido, de path tra;
PATH errado, ou de erro de tipo na validação de dados.

Precisávamos de uma hierarquia de exceções para que camadas superiores (clia, UI) as tratassem adequadamente.

## Decisão

Criar uma hierarquia de exceções de domínio única:

```python3
EDYShieldError (raiz)
├── HashError                 # falhas de domínio de hashing
│   └── UnsupportedAlgorithmError
├── ValidationError           # entradas inválidas
│
└── FilesystemError           # filesystem seguro

PluginError (plugins domain)
  ├── PluginNotFoundError
  ├── PluginRegistrationError
  └── PluginExecutionError
```

Regras:

1. Nunca lance `ValueError`, `TypeError`,  `FileNotFoundError`, etc. para erros de domínio — traduza para um EDYShieldError concreto
2. CLI/T tratarão só pela hierarquia de domínio (nada de raw traceback do usuário)
3. Erros de instanciamento de terceiros nunca são repassados diretamente ao usuário

## Consequências

### Positivas
- ✅ CLI trata `EDYShieldError` e `FileNotFoundError` com logs limpos, separadamente
- ✅ Logger consegue diluirErros por categoria (HashError → gravidade MÉDIA)
- ✅ Camada de plugin trata erros de domínio com prefixo de plugin

### Negativas (tradeoffs)
- ⚠️ A camada em \,VOLUME de erro — para tratamento de erros simples há 3 níveis
- ⚠️ Muitas exceções implicam acoplamento a `exceptions/domain` em vários módulos
