# ADR-006: Camadas do Core por responsabilidade

## Contexto

Na Sprint 1, toda a lógica do Hash Checker vivia em um único módulo
`app/core/algorithms/hash_checker.py` (cálculo, whitelist de algoritmos, comparação segura,
validação de paths, validação de entradas e hierarquia de erros). Com o crescimento planejado
da plataforma (File Integrity Monitor, String Analyzer, dashboard, API), um único módulo
centralizador dificultaria:

- a **testabilidade** isolada de cada responsabilidade;
- a **evolução** sem risco de regressão (ex.: mudar validação de paths não deveria tocar o
  cálculo de hash);
- a **aplicação consistente** da fronteira de segurança (um único ponto para paths);
- a **clareza de dependências** entre conceitos distintos (crypto ≠ filesystem ≠ validators).

Além disso, a revisão de segurança do ARES (ARES-QA-001..018) apontou que a fronteira de paths
precisava existir de forma explícita e única, e a re-review da fundação (ARES-QA-019..024)
reforçou a necessidade de organização em camadas antes da v1.1.

## Decisão

Criar **camadas do Core por responsabilidade**, cada uma em um pacote próprio dentro de
`app/core/`, e mover a lógica de hash/path/validação para módulos especializados:

```text
app/core/
├── algorithms/     → API pública (hash_checker delega para as camadas abaixo)
├── config/         → Settings frozen + load_settings (variáveis EDY_*)
├── crypto/         → HashAlgorithm, normalize_algorithm, new_hasher, safe_compare
├── exceptions/     → EDYShieldError → HashError/ValidationError/FilesystemError
├── filesystem/     → resolve_safe_path, ensure_regular_file (fronteira única de paths)
├── logging/        → setup_logging, get_logger
├── models/         → HashResult, HashSource (+ shims de erros)
├── report/         → RESERVED (sem código)
├── validators/     → validate_chunk_size, validate_expected
└── utils/          → RESERVED (sem código)
```

Princípios adotados:

1. **Fonte canônica única** — cada conceito tem um módulo canônico (`crypto/hashing.py`,
   `filesystem/safe_path.py`, `exceptions/domain.py`, `config/settings.py`, ...).
2. **`hash_checker` delega** — a API pública `app.core.algorithms` mantém os mesmos 8 símbolos,
   mas agora orquestra as camadas internas (crypto + filesystem + validators + exceptions).
3. **Shims preservados** — `app.core.models.common` e `app.services.file_utils` re-exportam da
   fonte canônica para não quebrar imports existentes.
4. **Nenhuma abstração sem uso** — `report/` e `utils/` foram criados como estrutura reservada,
   **sem código**, evitando abstrações prematuras (ADR-001).

## Consequências

### Positivas

- ✅ **Responsabilidade única** por módulo — mais fácil testar, revisar e evoluir.
- ✅ **Fronteira de segurança única** (`filesystem`) — qualquer operação de arquivo passa por
  `resolve_safe_path` + `ensure_regular_file` (ARES-QA-001/005/007).
- ✅ **Direção de dependências clara** — `algorithms → {crypto, filesystem, validators,
  exceptions}`; nada no core importa de `services`/`cli`/`ui`.
- ✅ **API pública preservada** — consumidores existentes continuam funcionando (shims).
- ✅ **Cobertura 99.34% e mypy strict 0 issues** no estado Sprint 2 — camadas testáveis.

### Negativas / custos

- ⚠️ **Mais arquivos/pacotes** — aumenta a superfície de organização inicial.
- ⚠️ **Indireção para chamadores** — imports canônicos mais profundos
  (`app.core.exceptions.domain` em vez de `app.core.models.common`); mitigado pelos shims.
- ⚠️ **Risco de ciclos de import** — exige disciplina: `filesystem` não importa `algorithms`
  (documentado no docstring de `safe_path.py`).
- ⚠️ **Shims podem confundir** se receberem lógica nova — regra explícita: shims **não
  acumulam** lógica (vai para o Core).
