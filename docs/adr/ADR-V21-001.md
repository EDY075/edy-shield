# ADR-V21-001 — SQLite como backend de persistência (History/Fim)

> **Status:** Aceito · **Data:** 02/08/2026 · **Autor:** jr (Software Architect) + ATLAS
> **Aplicável a:** v2.1 (M1 — SQLite Foundation)

## Contexto

O EDY Shield persistia `ScanResult` (HistoryStore) e `Baseline` (FimStore) como
**JSON por arquivo** em `~/.edyshield/{history,fim}/`. Essa abordagem funcionava, mas
apresentava limitações:

- **ARES-QA-033**: `baseline_id` com granularidade de segundos → duas baselines no
  mesmo segundo colidiam (a segunda sobrescrevia a primeira).
- Agregação para Dashboard/KPIs exigiria ler N arquivos JSON e agregar em memória.
- Alertas (v2.1-M3) precisariam de persistência consultável e relacional.

## Decisão

Adotar **SQLite** (`sqlite3` da stdlib) como backend de persistência, com:

1. Novo módulo `app/core/storage/` (SQLiteDb) — conexão thread-safe, schema,
   transações atômicas.
2. `HistoryStore` e `FimStore` passam a usar SQLite, **preservando contratos
   públicos** (assinaturas + `db_path` opcional).
3. Migração automática e idempotente de JSON legado → SQLite; arquivos originais
   movidos para `~/.edyshield/backup/`.
4. Fallback de leitura legada (JSON) quando o id não está no SQLite.
5. Colisão de `baseline_id` resolvida com id único (fração de microsegundos).

## Motivo

- **ADR-001 preservado**: `sqlite3` é stdlib — zero dependências runtime.
- **Fundação transversal**: Alertas (M3) e Dashboard (M4) dependem de persistência
  relacional; construir a fundação primeiro (M1) elimina retrabalho.
- **Robustez**: transações, FKs, WAL, consultas por timestamp/severidade.
- **Sem quebra de contrato**: plugins, UI e CLI inalterados (mesmos endpoints/ids).

## Alternativas consideradas

| Alternativa | Motivo de rejeição |
|-------------|--------------------|
| Manter JSON | Não resolve ARES-QA-033; agregação ineficiente; sem FKs |
| `duckdb`/`tinydb` | Dependência externa — violaria ADR-001 |
| Microsserviço de storage | Overkill para produto desktop/CLI single-user |

## Consequências

- **Positivas:** ARES-QA-033 resolvido; histórico consultável; base para M3/M4;
  banco único `~/.edyshield/edy_shield.db`.
- **Negativas/riscos:** SQLite single-writer (aceito — produto single-user);
  migração exige cuidado (mitigada por idempotência + backup + fallback).

## Implementação

- `app/core/storage/sqlite_db.py` — SQLiteDb (schema `scans`, `baselines`,
  `baseline_entries`; RLock + conexão por operação; WAL; FK).
- `app/services/history.py` — HistoryStore → SQLite + migração + fallback.
- `app/core/fim/store.py` — FimStore → SQLite + migração + fallback + id único.
- `app/core/fim/ids.py` — `build_unique_baseline_id` (fração de microsegundos).
