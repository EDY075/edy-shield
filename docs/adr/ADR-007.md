# ADR-007: CLI via argparse (stdlib) com subcomandos

- **Status:** Aceito
- **Data:** 2026-08-01
- **Decisores:** jr (Tech Lead), ATLAS (Arquiteto)
- **Implementação:** VULCAN (Missão 3 da Sprint 2)
- **Documentação:** NOVA (Missão 4)

> **Nota de contexto:** a decisão inicial de usar `argparse` já estava esboçada como ADR-004
> (referenciado em `docs/ARCHITECTURE.md` §9, sem documento individual). Este ADR-007 registra
> formalmente a implementação **concluída** da CLI real.

## Contexto

O projeto precisava de uma **interface de linha de comando funcional** para o Hash Checker:
calcular hash de arquivo/texto e verificar integridade, instalável globalmente. Os requisitos:

- **Zero dependências de runtime** (ADR-001 — core 100% stdlib);
- Entrypoint instalável via `pip install -e .` (`[project.scripts]` no `pyproject.toml`);
- Comandos claros: `hash` e `verify` com subcomandos;
- Saída compatível com scripts (digest/`OK`/`FAIL` em stdout, logs em stderr);
- Códigos de saída simples: **0** sucesso, **1** erro de domínio/validação.

Na v1.0, o entrypoint `edyshield` apontava para `app.cli.hash_cmd:main`, mas o módulo **não
existia** — achado **ARES-QA-021** (bloqueante para release). A Sprint 2 precisava resolver isso.

Alternativas consideradas:

| Opção | Prós | Contras |
|-------|------|---------|
| **`argparse` (stdlib)** | Zero deps; suficiente para 2 subcomandos; maduro | Menos "bonito" que Click/Typer; autocomplete manual |
| **Typer** | DX rica, autocomplete, help bonito | **Dependência de terceiros no runtime** (viola ADR-001); peso extra |
| **Click** | Ecossistema maduro | Dependência externa; overkill para o escopo atual |

## Decisão

Implementar a CLI com **`argparse` da biblioteca padrão**, com subcomandos `hash` e `verify`,
em `app/cli/hash_cmd.py`, exposta pelo entrypoint `edyshield`:

```text
edyshield hash <path> [--algorithm SHA256|SHA1|MD5] [--root DIR]
edyshield verify <path> --expected <HASH> [--algorithm SHA256|SHA1|MD5] [--root DIR]
edyshield --help
edyshield --version            # edyshield 1.1.0
```

Regras de contrato:

- Exit codes (ARES-QA-029):
  - **0** = sucesso (hash calculado / verificação MATCH)
  - **1** = verificação MISMATCH (apenas comando ``verify``, hash calculado mas diferente do esperado)
  - **2** = erro de domínio / validação / exceção inesperada
  - ``--help`` / ``--version`` = 0 (SystemExit do argparse)
- **stdout**: hexdigest (`hash`) ou `OK`/`FAIL` (`verify`); **stderr**: logging + `erro: ...`.
- `--algorithm` default = `settings.default_hash_algorithm` (env `EDY_DEFAULT_HASH_ALGORITHM`).
- `--root` default = **diretório pai do arquivo alvo** (quando não informado), mantendo a
  contenção da fronteira (ARES-QA-001).
- `--version` expõe `app.__version__` (`edyshield 1.1.0`).
- Logging centralizado via `setup_logging(settings)` (Missão 3).

**Typer** permanece como **evolução futura opcional** (v2+), somente se a UX do CLI crescer a
ponto de justificar a dependência — nunca no runtime da v1.

## Consequências

### Positivas

- ✅ **ARES-QA-021 resolvido** — `pip install -e .` instala e `edyshield` funciona.
- ✅ **Zero deps runtime mantido** (ADR-001) — CLI é stdlib puro.
- ✅ **Testável** — `main(argv)` retorna `int`; suíte `tests/unit/test_cli.py` cobre `--version`,
  `--help`, `hash`, `verify`, erros e exit codes.
- ✅ **Compatível com scripts** — saída estável em stdout + códigos 0/1.

### Negativas / custos

- ⚠️ **UX limitada** vs. Click/Typer (autocomplete, help avançado) — aceito para o escopo.
- ⚠️ **`main()` intercepta `SystemExit` do argparse** (`--help`/`--version`) e o converte em
  código de saída — leve indireção para manter testabilidade.
- ⚠️ **Crescimento futuro** pode exigir migração para Typer/Click — a separação em
  `cli/hash_cmd.py` + `core` (lógica pura) mantém essa migração barata.
